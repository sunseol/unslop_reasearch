# Unslop 문서 저장소

Unslop의 사업과 제품을 계획하고, 결정의 근거와 문서 간 관계를 남기는 저장소입니다. 출발 문서는 [사업계획서](unslop_business_plan.md)입니다. 이 README는 사람이 저장소를 이해하고 관리하기 위한 공통 규칙입니다.

## 파일 구성

문서 본문은 Markdown으로 작성하고, 문서가 있는 각 폴더의 `_index.yaml`에 해당 폴더 문서의 정보와 관계를 기록합니다. 이전본은 그 문서가 있던 폴더의 `_old/`에 보관합니다. 필요한 폴더만 만들며 빈 영역 폴더를 미리 만들지는 않습니다.

```text
README.md
_index.yaml
unslop_business_plan.md
01_사업_방향/
  _index.yaml
  문제_정의.md
  _old/
    문제_정의__20260908T143000+0900.md
scripts/
  check-docs.mjs
```

위 영역 폴더는 예시입니다. 향후 계획은 사업 방향, 문체 품질 기준, 데이터와 평가, 기술 엔진, 제품과 사용 경험, 사용자 확보와 수익화, 실행과 운영으로 나눕니다.

## 문서 등록과 관계

모든 현재 Markdown 문서는 같은 폴더의 `_index.yaml`에 등록합니다. README도 포함합니다. `_old/`의 이전본은 등록하지 않습니다.

```yaml
documents:
  - id: strategy-001
    file: 문제_정의.md
    status: active
    summary: Unslop이 해결할 문제와 초기 범위
    depends_on: []

  - id: strategy-002
    file: 초기_고객.md
    status: draft
    summary: 초기 고객 후보와 선정 근거
    depends_on:
      - strategy-001
```

- `id`: 저장소 전체에서 고유한 소문자 영문·숫자·하이픈 식별자입니다. 이름이나 위치가 바뀌어도 유지하고, 폐기한 ID는 재사용하지 않습니다.
- `file`: YAML이 있는 폴더 기준 경로입니다. 현재본은 바로 아래의 `.md` 파일, 폐기본은 `_old/` 바로 아래의 `.md` 파일을 가리킵니다.
- `status`: 작성 중은 `draft`, 현재 기준으로 채택하면 `active`, 폐기하면 `retired`입니다. 최초 사업계획서는 아직 가설을 포함하므로 `draft`로 등록합니다.
- `summary`: 문서 목적을 한 문장으로 씁니다.
- `depends_on`: 이 문서의 판단이 의존하는 문서 ID 목록입니다. 없으면 `[]`로 씁니다. 폴더가 달라도 경로 대신 ID로 참조합니다.
- `supersedes`: 다른 문서를 대체할 때만 추가하는 ID 목록입니다. 대체된 문서는 `retired`로 남깁니다. 같은 문서의 단순 수정에는 사용하지 않습니다.

관계는 의존하거나 대체하는 쪽에서만 기록합니다. 대상 ID는 YAML에 등록되어 있어야 합니다. 역방향 관계는 중복 작성하지 않습니다. 두 관계 종류를 합친 그래프에서 자기 참조와 순환을 허용하지 않습니다. 현재 문서는 폐기된 문서에 의존할 수 없습니다. 폐기 시 의존 문서를 함께 검토합니다.

ID·상태·관계의 기준은 YAML입니다. Markdown에 같은 메타데이터를 다시 작성하지 않습니다. 본문에서 읽기 편한 문서 링크를 넣는 것은 허용합니다. 내부 링크는 저장소 안의 상대 경로를 사용합니다. HTML 대신 Markdown 문법으로 작성합니다.

## Markdown 양식

```markdown
# 문서 제목

문서의 목적과 현재 결론을 한두 문장으로 설명합니다.

## 본문
목적에 맞는 소제목으로 내용을 구성합니다.

## 근거
판단에 사용한 자료, 관찰, 관련 문서 링크를 남깁니다.

## 미결 사항
아직 결정하지 않은 내용과 결정에 필요한 조건을 씁니다.
```

빈 항목은 생략합니다. 사실·가설·결정은 문장으로 구분합니다. 예를 들어 “초기 고객을 PM으로 가정한다. 인터뷰 후 확정한다”처럼 판단의 상태가 드러나게 씁니다. 별도 변경 일지나 핸드오프 문서를 반복 작성하지 않습니다.

## 수정·이동·폐기

1. 기존 문서를 바꾸기 전에 현재 브랜치의 `HEAD`에 있는 현재본을 같은 폴더의 `_old/`에 복사합니다. 파일명은 `원래이름__YYYYMMDDTHHMMSS+0900.md`처럼 보관 시각과 시간대를 붙입니다. 같은 이름이 있으면 초 단위 시각을 갱신하고 덮어쓰지 않습니다.
2. 현재 파일을 수정하고 YAML의 요약·상태·관계를 필요에 따라 갱신합니다. 같은 커밋을 준비하며 여러 번 수정해도 이전본은 한 번만 보관합니다. 아직 커밋되지 않은 신규 문서에는 이전본이 필요 없습니다. 오탈자 수정도 같은 규칙을 적용합니다.
3. 이동·이름 변경 시 이전본은 원래 폴더에 남기고, 현재본의 YAML 항목은 목적지 폴더로 옮깁니다. ID를 유지하고 본문 링크도 갱신합니다.
4. 폐기 시 현재본을 `_old/`로 이관하고, 기존 YAML 항목의 `status`를 `retired`로 바꾸며 `file`을 보관 경로로 갱신합니다. 파일 내용이 완전히 같은 이전본을 이미 만들었다면 중복 보관하지 않습니다. 이후 복구는 같은 ID의 현재본을 만들고 `draft` 상태와 현재 경로로 갱신합니다. 다시 채택하면 `active`로 바꿉니다.
5. 검사 후 본문·YAML·이전본을 하나의 변경 목적에 맞춰 함께 커밋합니다.

이전본은 수정하지 않습니다. 과거 링크가 현재 구조와 달라도 그대로 보존합니다. YAML 자체와 코드·설정 파일의 이전 버전은 Git으로 관리하며 `_old/`에 복제하지 않습니다. `_old/`는 Git에 포함합니다.

## 커밋으로 인계하기

제목은 `docs(문서ID 또는 영역): 변경 요약`으로 씁니다. 검사 코드나 설정 변경에는 `chore(docs)`를 사용합니다. 한 커밋에는 설명 가능한 하나의 변경 목적을 담습니다.

```text
docs(strategy-002): 초기 고객을 업무보고 작성자로 좁힘

변경: 고객 범위와 선정 기준을 수정했다.
이유: 기존 후보군은 문서 유형과 사용 목적이 너무 달랐다.
영향: Challenge 과제 구성 문서의 재검토가 필요하다.
다음: 인터뷰에서 보고서 수정 빈도와 소요 시간을 확인한다.
```

`변경`과 `이유`는 기록하고, `영향`과 `다음`은 해당할 때만 씁니다. 검토자는 `git log`로 판단의 흐름을 읽고 필요할 때 diff와 `_old/`를 확인합니다. 커밋 메시지 형식은 사람이 검토합니다.

## 자동 검사

Node.js 22와 npm을 설치한 환경에서 저장소 루트에서 실행합니다.

```sh
npm ci
npm run check:docs
```

검사기는 파일을 변경하지 않습니다. YAML 형식과 필수 필드, ID 중복, 미등록 Markdown, 파일 경로, 관계 대상·상태·순환, 현재 Markdown의 내부 링크 대상 파일 존재 여부를 검사합니다. 코드 블록 속 예시는 검사하지 않습니다. `_old/`, `.git/`, `node_modules/`는 현재 문서 검사 대상에서 제외합니다.

외부 URL 접속, `#제목` 앵커, 문서 내용의 타당성, 이전본 보관 누락, Git 커밋의 품질은 자동 검사하지 않습니다. 보관 여부는 커밋 전에 직접 확인합니다. YAML에서 `retired` 문서가 가리키는 보관 파일의 존재는 검사합니다.

GitHub에 올리면 push와 pull request에서 같은 검사가 실행됩니다. 검사기 자체의 회귀 검사는 `npm test`로 실행합니다. CI 실패를 병합 차단 조건으로 삼으려면 GitHub에서 브랜치 보호를 별도로 설정해야 합니다.
